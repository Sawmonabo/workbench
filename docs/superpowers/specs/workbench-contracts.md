# Workbench implementation contracts

Status: implemented contracts and qualification requirements, 2026-09-22. See the [design](workbench-design.md) for architecture, [usage](../../usage.md) for commands, and [acceptance](../../acceptance.md) for observed checks and remaining gates. Isolated checks are not live-machine provisioning or production-release certification.

## Runtime paths and context

Directory overrides are `WORKBENCH_CONFIG_DIR`, `WORKBENCH_DATA_DIR`, `WORKBENCH_STATE_DIR`, `WORKBENCH_CACHE_DIR` and `WORKBENCH_BIN_DIR`, each an absolute Workbench directory. Explicit overrides win; otherwise use the applicable absolute XDG base plus `/workbench`; otherwise use these defaults:

| Purpose | Linux/WSL default | macOS default |
| --- | --- | --- |
| Config | `~/.config/workbench` | `~/Library/Application Support/workbench/config` |
| Data | `~/.local/share/workbench` | `~/Library/Application Support/workbench/data` |
| State | `~/.local/state/workbench` | `~/Library/Application Support/workbench/state` |
| Cache | `~/.cache/workbench` | `~/Library/Caches/workbench` |
| Entry point | `~/.local/bin/workbench` | `~/.local/bin/workbench` |

Data holds `releases/<release-id>-<archive-hash-prefix>/`, private `tools/<tool>/<version>/` and private source application contexts. Config holds `machine.toml` (native `[data]` answers). State holds `state.json`, `chezmoi/chezmoi.boltdb`, operation journals/checkpoints and lock metadata. Cache holds bounded disposable downloads/render scratch. Config/state directories are 0700 and secret-bearing files 0600; missing parents of them, such as `~/.config` or `~/.local`, are created 0755. Workbench runs with the user's umask plus 022, as sudo does, so nothing it or its tools create is group- or world-writable: its checks refuse such parents, tools and targets, and Ubuntu logins default to umask 002. An existing parent that others can write to stops Workbench with the folder and the `chmod go-w` that fixes it. WSL private state stays on the Linux filesystem; Windows target protection needs Windows ACL verification, not a claim that POSIX chmod suffices.

The hidden `--local-build` takes no value and selects the developer tree: the nearest ancestor of the current directory holding `.chezmoiroot` and `go.mod`, or exit 2 outside one; `--destination PATH` selects a configuration destination. Default destination is the actual current user's home. Full provisioning rejects an alternative destination because current scripts write `$HOME`, platform directories and external state independently of chezmoi's destination. Isolated full smoke tests therefore need a disposable OS user/VM. Reject relative runtime overrides, unsafe ownership, escaping symlink parents, source/destination aliases, targets overlapping source/runtime/state, unsupported state and non-regular input files before mutation. Runtime directories may live beneath the destination home but are never managed target paths. No recursive cleanup is authorized by an override.

Every chezmoi invocation supplies explicit `--source`, `--config`, `--destination`, `--persistent-state`, `--cache`, `--no-pager`, `--use-builtin-diff` and `--refresh-externals=never`. Source is the selected context root containing `.chezmoiroot`, not a guessed home source directory. Native config output contains `sourceDir = .../home`; retain answers as `[data]` only after validation, so Workbench's release/context selector remains authoritative. Existing configuration adoption copies validated data only, with explicit approval; never inherit arbitrary native hooks, external commands, source selection or Git auto-push configuration.

Previews, doctor and inspection do not create persistent state, native Git metadata, or missing answers. Any render scratch is ephemeral/private with copied native state; never invoke mutating native commands against live state to implement a preview. Audit template `output`, `lookPath`, modify executables and host probes separately from provisioning scripts. `--exclude scripts` still executes Python modify programs and evaluates templates. The WSL questionnaire makes host sizing probes conditional on missing values; only reviewed read-only probes are permitted. Do not open editors, remote sessions or repository code during discovery.

Release source render trust is the machine source digest `scripts/package-release.py` writes into `release.json` and stamps into that release's executable: the SHA-256 of one `<sha256>  <path>` line per `.chezmoiroot`/`home/` file, sorted by path. A release source (one with `release.json`) whose files, metadata or executable stamp differ is rejected, an unstamped build accepts no release source, and filename recognition alone cannot authorize executing a modify script during preview. A developer checkout selected with `--local-build` is the user's own tree: it is bound by its actual content digest, which enters the approved plan, so its templates render during preview like `chezmoi diff` would. A private verified source selection handles role-driven native removals without introducing another renderer. Runtime ancestors can be validated containers. Native may change only such a directory's mode, and only to one without group or other write; the plan lists it as a mode-only edit, and its checkpoint lets revert restore the mode. Nothing may remove or replace them. When a checkpoint cannot record such a folder, as for macOS flags on `~/Library`, the plan stops with the `chmod` that matches the configuration; within the shared bin directory only the Workbench entry point is reserved.

## Native initialization

[Native init](https://www.chezmoi.io/reference/commands/init/) always initializes a Git repository when `.git` is absent. In v2.70.3, [the implementation](https://github.com/twpayne/chezmoi/blob/v2.70.3/internal/cmd/initcmd.go) supports the built-in Git path. There is no `--no-git` flag. `execute-template --init` supplies simulated prompt functions; it is useful for fixtures but is not the interactive questionnaire.

Use this native sequence in the setup stage of `apply`. `update` installs the release and the pinned tools only and never runs it:

1. Verify the release archive; create a private application-context copy of its source, retaining the verified payload content hash. Staging and activation inside `update` do not perform this initialization.
2. Create a private native seed TOML containing validated existing `[data]` answers, or an empty seed for native terminal prompting. Do not put secret answers in command arguments or prompt-text flags. The canonical template owns conditional questions and derived role/WSL values.
3. Execute the following with absolute, prevalidated paths, no repository argument and no `--apply`:

   ```sh
   chezmoi --use-builtin-git=true --config "$seed" \
     --source "$context" --destination "$destination" \
     --persistent-state "$private_state" --cache "$private_cache" \
     init --config-path "$generated_config"
   ```

4. Validate the generated TOML/answers; atomically record private answers only. Recheck source payload identity and seal that context before target planning/application. Native `.git` metadata and host answers are excluded from payload identity and distributable assets. Do not exclude arbitrary source changes from identity merely because native metadata exists.

Probe evidence: on macOS 27.0 arm64, an extracted `git archive` of the source (no `.git`) plus complete private `[data]` inputs initialized without questions using `--no-tty`, generated a 0600 config, and applied files into a disposable destination with `--exclude scripts`, including the Python Codex modify program. A repeat init produced identical configuration. Native empty `.git` occupied 8 KiB in this probe, not a size guarantee. No remote or commits were created. A separate unrelated working-tree directory failed native containment validation. A `git.command=/usr/bin/true` experiment avoided metadata but is explicitly rejected as the product path; do not mask native operations with no-op executables.

Serialization contract: the canonical questionnaire uses structured native TOML serialization. Native `dict "name" .name | toToml` round-tripped quotes, backslash, comma, equals, newline and Unicode exactly. The implementation uses native `toToml` on structured data, preserving the canonical questions. Validate role/editor/mode rather than silently normalizing invalid persisted answers. Validate sizing strings, integer bounds and restart paths before downstream scripts. Machine identity fields reject control characters/newlines even though the serializer can represent them. Structured serialization is also required at each downstream TOML/JSON/Git/shell/PowerShell boundary: escaping the seed alone does not fix Python triple-quoted generated code, raw Git identities, shell substitutions or PowerShell quoting. Invalid Codex TOML now fails without replacement. Do not reintroduce permissive fallback behavior.

## Consent and output

Select `--non-interactive`, `--approve-plan SHA256` and `--json` for automation. Without a terminal, mutation requires complete answers (saved with `init --answers-from FILE`) and the matching plan digest; `--yes` applies the saved selection for a person who trusts it and is not a substitute for reading the plan. Interactive `apply` approval follows the same displayed plan: a huh v2.0.3 multi-select checklist of the effects on the controlling terminal with the plan's checks as defaults, where Enter applies exactly that selection and esc and ctrl+c refuse; when no effect can be chosen it is a Yes/No prompt with No selected first. `revert` and `project` use that Yes/No prompt, where Enter alone, n, esc and ctrl+c all refuse. Recovery without `--checkpoint` offers the saved checkpoints in a huh picker at a terminal and otherwise lists them and blocks. `apply` asks for one approval, of the checked machine plan; `update` asks none, because it changes only Workbench's own files and keeps the replaced release, and `update --dry-run` still shows the install plan. Installing the release and setting up Workbench's pinned private tools need no separate approval, because running the command requests them. The native questionnaire asks only what the saved answers lack, or what `init --ask` names, and its answers never authorize configuration or provisioning. Cancelling it with esc or ctrl+c saves nothing and blocks, naming `workbench apply`. If full preview needs missing prerequisites, return blocked and name `workbench apply`, which sets them up and then produces the machine plan for approval. Missing unattended answers fail; never accept native prompt defaults silently. Prompt values stay off argv and out of logs.

The digest binds release/source content, dependency choices, which effects are checked (a changed saved selection returns conflict, exit 4), canonical destination/project scope, native input/state hashes, current target images, file removals, external effects and selected privilege. Recompute it before writes; a changed input returns conflict. Do not persist low-entropy secret hashes in public output; expose only an opaque aggregate plan identity and redacted descriptions. Latest-mode provider changes that broaden the plan require renewed approval.

Ordinary apply includes selected configuration/provisioning only. Cleanup, tap removal, app updates, extension conflict removal, Windows registry/environment/default-distribution changes and system tuning must appear as individually named effects with recovery limitations. A plan lists a provisioning effect only when native chezmoi would run one of its scripts or change one of its files (`effectSources` in `internal/machine/effects.go`), so a once-only script that already ran is not presented as work; an effect without sources is always listed. Homebrew cleanup and tap removal (`brew-maintenance`) are a named effect of every full macOS plan; Windows host changes and system tuning stay disabled until explicitly selected; each listed app or formula Homebrew reports as outdated is its own named update effect, except formulae providing the chezmoi, uv or Python Workbench runs or whose upgrade would change them; a formula's effect names the other formulae Homebrew's dry run says its upgrade installs or updates, and the apply step sets `HOMEBREW_NO_ASK` so plan approval is the only prompt; apps installed outside Homebrew are left alone; blanket unattended approval does not enable an omitted effect. No services/WSL restart, scheduled-task execution, credentials authentication or security-policy weakening is implied by setup. Existing AI trust/permission settings and Bitwarden session caching are security-sensitive configuration effects and must be visible for controller/user policy ratification; this contract does not independently approve a new security policy.

Human output uses stdout for results and stderr for diagnostics/progress. At a terminal, planning, the recheck after approval and tool setup show one live status line (spinner, step, elapsed time) drawn by an inline Bubble Tea v2.0.10 program with a Bubbles v2.2.1 spinner and Lip Gloss v2.0.6 styles; it reads no input, so it sends no terminal queries and leaves the terminal mode and ctrl+c/ctrl+z alone, and it clears before any prompt or terminal handoff. Otherwise each step prints as a plain line. An interrupt during planning ends it with the interruption code, even inside probes whose failure only warns. A plan prints as a readable review of files, effects with their privilege and recovery, warnings and recovery limits, and `--json` carries the complete plan. At a terminal, component results carry a colored ✓, · or ✗, a successful run ends with a green ✓ summary (the result's `summary`), and a plan already shown at an approval prompt is not repeated; piped output and `NO_COLOR` get plain text. An interactive apply gives native chezmoi the controlling terminal as the foreground process group, so sudo and installers can prompt and their output appears live, then takes it back with SIGTTOU ignored so a job-control shell does not stop Workbench; unattended runs stream redacted output lines on stderr. Neither has a deadline: provisioning runs until done or interrupted, and the caller's supervisor owns any time limit. Captured probes stay bounded and report a failed tool's redacted stderr tail. `--json` emits one JSON object, no ANSI/subprocess stdout mixed in: `schema_version: 1`, `command`, `status`, `results`, `warnings`, `errors`, with `operation_id`/`plan_digest` when applicable. Component results distinguish `complete`, `unchanged`, `blocked`, `failed`, `skipped` and `conflict`, including recovery coverage. Errors carry a stable category and actionable redacted message; no secret-bearing raw diff or full environment/argv dump. JSON mode still needs consent and must work without interactive prompts.

| Exit | Meaning |
| --- | --- |
| 0 | Entire requested supported scope completed, including an unchanged result |
| 1 | Execution/check failure without a completed partial mutation |
| 2 | Invalid invocation/input or unsupported current Workbench format |
| 3 | Blocked: prerequisites, support, policy or consent missing |
| 4 | Plan/input/recovery conflict; no new mutation |
| 5 | Partial mutation, including requested work skipped after writes |
| 130 | Interrupted; journal separately records any partial writes |

## Checkpoints and current state

Use random operation/checkpoint UUIDs, recording scope (`machine` or canonical project root), creation time, before/applied release identity (for project checkpoints, the policy ID such as `python-v1`), pre-images, post-images and effect results. `revert` and `project revert [PATH]` see only that scope's checkpoints. `revert --checkpoint ID` and `project revert [PATH] --checkpoint ID` restore that operation's pre-images after full preflight. With no selector, a terminal picks one from the list, otherwise the list is shown and an explicit selection is required. An unknown ID fails with the IDs to choose from. A checkpoint with unknown post-images after interruption requires reviewed reconciliation, not inferred success or blind restore.

Preflight every target before restoring any, record type/mode/group/link target as well as bytes, and stop on later edits or unsupported filesystem metadata. Hard links, special files, escaping symlinks, unverified ACL semantics and broad directory replacement are blocked until preservation is supported. Native machine planning rejects output modes granting group permissions beyond other permissions, such as 0640/0750: native temporary-file ownership cannot yet preserve those atomically. For supported modes, descriptor-bound exact-image checks precede any post-native group correction. The shared project/recovery writer sets group before chmod and atomic replacement. Revert creates its own recoverable operation. It does not run the old release, native provisioning scripts or project dependency hooks. Packages, extensions, user environment/registry, loaded fonts, kernel values and external services are outside file recovery even if nearby configuration files are restored.

Retention: each scope keeps the 20 most recent **forward-operation** checkpoints. Before each forward mutation, reserve its paired recovery record and bounded journal capacity as well as its image storage. At 20, the plan lists removal of the oldest settled (complete or failed) checkpoint and its pair as a named `checkpoint-retention` effect, so consent covers it; the removal happens under the held locks just before the new checkpoint is reserved. Running, partial and unknown checkpoints are never removed, and recovery of retained checkpoints stays available. The recorded partial operation stays until a later approved apply to the same destination finishes or recovery restores its checkpoint; an apply with no target changes settles it because its plan found every target already matching, and one to another destination is blocked while it stays. No age-based deletion. An apply with no target changes allocates no checkpoint; one whose files all match, with no effect checked, no changed selection to save and no recorded partial operation to settle, writes nothing, so it asks for no approval and says `Nothing to apply; this machine already matches`. Users never need to delete checkpoint files to recover.

Recovery uses the reserved pair, not another forward slot: retain the original checkpoint and one separately selectable recovery checkpoint with reversed pre/post-image references. Each scope therefore has at most 20 forward and 20 paired recovery checkpoints. Restore, undo-of-restore and retries reuse that pair's bounded resumable journal; they do not recursively allocate checkpoints. A new recovery attempt has its own operation identity and current progress, and may replace a completed attempt's journal only after both image sets and the selectable recovery checkpoint remain durable. An interrupted attempt must resume or reconcile before reusing its journal. Preserve known per-target images after partial application; unknown post-images still require reviewed reconciliation under the existing conflict rule. This bounds recovery storage without deleting either checkpoint or sacrificing the ability to undo a completed restore.

Conservative implemented caps: 256 targets, 8 MiB per image, 32 MiB aggregate raw pre/post images per forward operation, 50 MiB serialized per pair and 1 GiB per scope. Reserve two 64 KiB journal slots and two 1 MiB metadata slots before target writes. Refuse forward mutation if images and protected recovery capacity cannot fit. The measured source corpus was about 156 KiB with a 24,417-byte largest file; a representative native uv lockfile was 9,988 bytes. This supports headroom for those fixtures, not a universal capacity/performance claim. Native release qualification remains open. There is no separate cleanup command; plan-approved retention is the only removal.

Persist `schema_version: 1` in current state/journals and validate all required fields, identities, scopes and image references before use. Unknown versions or malformed state stop without conversion/deletion. A single private active-release record selects a matched executable/source release. Each record replacement is atomic, but activation also changes the entry-point symlink: a private journal detects interrupted mismatches and requires explicit install resumption. Preserve the prior verified runtime; never claim whole-filesystem atomicity. After a successful activation, delete only the plan-listed older releases (keeping the new and replaced releases), and the setup contexts and private tool versions that no kept release or recorded dependency uses. A partial apply retains the prior successful configuration identity plus a partial-operation record. Hold shared release/state and selected scope locks in consistent order and recheck filesystem inputs; external package managers are not transactional. No compatibility matrix or migration layer.

## Project editors

Go retains discovery, planning, consent, checkpoints, all filesystem writes and native package-manager execution. One bounded batch text transform per operation is sufficient; format libraries never receive authority to write project files or run project code.

Do not recreate a TOML editor with regex or unstable token rewriting to avoid the Python library dependency.

Pin TOML Kit in the single management dependency owner, with verified wheel hash/license in generated release metadata. Its adapter is an internal text-in/text-out function, no user-facing CLI or separate installer. Run isolated Python (`-I`), with fixed trusted module paths, private environment, bounded stdin/stdout and no project imports/site customization. Preview reports a missing adapter without downloading it. Project discovery itself remains Go/native metadata reading and does not require executing a Python project. Parser errors stop the whole selected plan, and serialize/reparse/validate every proposed document before committing writes.

Initial configuration supports existing uv Python projects and uv workspaces with an identified shared lockfile; other languages/managers are discovery-only. Resolve separate Ruff/ty/basedpyright configs first and stop on competing owners. A selected child does not authorize root writes. Use uv's own dependency/lock operations only after separate effects approval; no project initialization. Mixed-language members stay intact. Record portable provenance in the project-owned `pyproject.toml` as `[tool.workbench]` with integer `schema_version = 1` and `policies = ["python-v1"]`; no absolute host paths or Workbench runtime dependency. Reject unsupported provenance versions; do not migrate them.

Project dependency resolution uses private metadata staging only after explicit `--resolve-dependencies` consent. `--allow-build-hooks` separately selects potential native code execution; uv `--no-build` is not a sandbox. Default configuration requires existing locked checker dependencies. Unsupported custom resolution remains blocked. Optional CI edits support one existing GitHub workflow with explicit project Python selection and an identifiable existing test job; preserve that job and append owned checks, never fabricate a runner or second workflow.

## Release gates and short validation checklist

Release integrity requires target/version/content manifest validation, SHA-256 verification before extraction/execution, file-count/size limits, regular-file/directory-only payloads initially, and rejection of traversal, links, devices, duplicate members and mismatched expected layout. The in-bundle SHA-256 manifest only detects corruption; it does not establish publisher trust. By the owner's decision, releases publish on `v*` tags to a public repository, unsigned and with no redistribution license; native capacity qualification remains open. Implemented bundle limits are 128 MiB compressed/download, 256 MiB expanded, 4,096 archive members and 1 MiB metadata. Payloads include the matched executable/source, four portable Python policy files, generated requirements and linked dependency/runtime license notices. The bundle NOTICE grants no Workbench redistribution license, and no signing identity is used.

Use the existing `scripts/render-check.sh` and CI job. The helper owns isolated source/config/destination/cache/persistent-state paths; a temporary destination alone is not enough. Reuse role/mode rendering and simulated WSL syntax checks. Simulation on macOS does not prove native Linux provisioning or Windows execution; current results belong in the acceptance record.

For each qualified native target, record OS/CPU/tool versions and a short disposable-user smoke: initialization without external Git; all role/mode config renders; repeated approved apply convergence; denied/absent privilege; actual shell/Git/editor/theme/tmux/runtime/global-tool effects; explicit optional-effect denial; unchanged recovery and later-edit conflict. WSL additionally needs Windows home paths with spaces/non-C-drive layouts, Terminal/PowerShell preservation, private ACL checks and individually reported registry/PATH/default-distribution/sysctl effects. Never execute restart helpers merely to test their installation. Existing files/credentials must be synthetic. Short checks of missing prerequisites, incomplete inputs, malformed config, source/destination overlap and edited checkpoint targets establish safety boundaries; no new testing framework or broad lifecycle matrix.

Routine verification remains formatting/lint/build and brief manual probes. Introduce automated checks only where the implementation could cause catastrophic data loss, credential exposure or unauthorized execution. No performance superiority or resource budget is established by these probes. Additional managers/languages, native Windows, automatic maintenance, production capacity qualification and publication trust remain explicit later decisions; the affected operation stays blocked until its gate is met.
