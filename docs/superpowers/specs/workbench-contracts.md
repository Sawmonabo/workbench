# Workbench implementation contracts

Status: implemented contracts and qualification requirements, 2026-09-22. See the [design](workbench-design.md) for architecture, [usage](../../usage.md) for commands, and [acceptance](../../acceptance.md) for observed checks and remaining gates. Isolated checks are not live-machine provisioning or production-release certification.

Management metadata lives under `home/.chezmoidata/versions.toml`. Workbench reads it at runtime from the selected machine source (`--local-build`, else the active release, with that source's usual checks), and each `release.json` carries a copy for tool cleanup; it reuses the uv/Python pins. A pinned chezmoi, uv, Python or TOML Kit version must be three dotted numbers and `tomlkit_url` an `https://files.pythonhosted.org/packages/` link, so an edited pin cannot move a download to another repository, host or uv option; every download is checked against the pinned SHA-256 before it is kept. `doctor` reports blocked tool versions when there is no source to read. Build tools are maintainer dependencies, never runtime prerequisites of the compiled CLI.

Resolution order is an already recorded compatible owner, then a compatible absolute executable discovered outside project-controlled PATH entries, then an explicitly approved private install. Borrowed chezmoi must be 2.70.3 for the initial verified contract; newer versions are reported unqualified without being replaced. Borrowed uv 0.11.21 or 0.12.3 and CPython 3.11–3.14 with working `tomllib` are eligible after bounded version/import checks. Unqualified tools are retained. Installing a private alternative alongside an incompatible existing tool is a separately disclosed choice, never an automatic duplicate or downgrade. Never execute a project-local shim to establish management compatibility.

One Go resolver records absolute path, observed version, installation owner and required capabilities. It supplies the selected bin directories through subprocess PATH and explicit paths through a private operation context; existing scripts consume that context and skip acquisition for a resolved dependency. Native package/runtime provisioning remains in its existing scripts. Remove unconditional chezmoi/uv entries from the generated Brewfile when a different owner already supplies them; do not add a second Go Homebrew/runtime installer. Direct chezmoi use may continue to use native script acquisition, but Workbench-managed execution must have one recorded installer owner. User-global uv tools and project environments remain separate from Workbench's private Python/library environment.

Before any target render/merge, preflight Python (`tomllib`), chezmoi and every selected library. Approved setup can install private uv/Python before native initialization and preview. The verified uv 0.11.21 interface is `uv python install --install-dir DIR --no-bin 3.12.12`, with a private `--cache-dir`; no shell-profile or global Python changes. A private tool or TOML Kit member is written to a `.NAME.partial` file beside its final path, flushed, then linked into place, so an interrupted install leaves no truncated tool at the final name; the next `update` or `apply` removes a leftover `.NAME.partial` and installs again. Existing modify scripts resolve `python3` through the selected operation PATH. A private tool-bin symlink is allowed; a replacement global `python3` is not. Native shell/status-line Python availability after apply must also be checked; a management-only interpreter does not automatically make an interactive `python3` command available.

Installer prerequisites are POSIX `sh`, `uname`, `mktemp`, `tar` and HTTPS `curl`, or a logged-in `gh`. `tar` extracts only the CLI; Go owns bundle verification and extraction, so runtime installation needs no Python or compiler. Detect them before download. Full platform provisioning additionally needs bash; Linux apt or dnf (chosen at run time: `apt-get` when present, else `dnf`) with sudo, on dnf EPEL for bat and fd (the `epel` step installs `epel-release` from AlmaLinux's `extras` repository), curl/unzip/git and fontconfig; macOS Homebrew/Xcode Command Line Tools; WSL `cmd.exe`, `powershell.exe`, `wsl.exe`, `wslpath` and Windows host access. A C compiler alone does not establish all Linux base prerequisites. Missing privilege/tooling is blocked work. Do not run setup as root. Clean Ubuntu and AlmaLinux bootstrap and private Python acquisition still require native smoke verification.

## Runtime paths and context

Directory overrides are `WORKBENCH_CONFIG_DIR`, `WORKBENCH_DATA_DIR`, `WORKBENCH_STATE_DIR`, `WORKBENCH_CACHE_DIR` and `WORKBENCH_BIN_DIR`, each an absolute Workbench directory. Explicit overrides win; otherwise use the applicable absolute XDG base plus `/workbench`; otherwise use these defaults:

| Purpose | Linux/WSL default | macOS default |
| --- | --- | --- |
| Config | `~/.config/workbench` | `~/Library/Application Support/workbench/config` |
| Data | `~/.local/share/workbench` | `~/Library/Application Support/workbench/data` |
| State | `~/.local/state/workbench` | `~/Library/Application Support/workbench/state` |
| Cache | `~/.cache/workbench` | `~/Library/Caches/workbench` |
| Entry point | `~/.local/bin/workbench` | `~/.local/bin/workbench` |

Data holds `releases/<release-id>-<archive-hash-prefix>/`, private `tools/<tool>/<version>/`, private source application contexts and the costs ledger with its price caches (`costs/`). Config holds `machine.toml` (native `[data]` answers, which hold no credentials: the retired `jira_api_token` and `gitlab_token` answers an earlier release saved stay there, redacted and carried through every write, until migration 0005 moves them into `work.env`), the role env files `work.env` and `personal.env` (0600, created by the `env-files` step when missing and the owner's after that) and the costs rate overrides (`costs/rates.json`). State holds `state.json`, `chezmoi/chezmoi.boltdb`, operation journals/checkpoints, lock metadata, the costs import log and lock (`costs/`), the agent command guard's notes, stop records and log (`guard/`) and the migration record (`migrations.json`). Cache holds bounded disposable downloads/render scratch and the shell completion script the startup files save (`completion.zsh` or `completion.bash`). The config, data, state and cache folders must be private (no group or other permissions) and owned by the user wherever they exist, or every command refuses to start; Workbench makes them 0700. The bin folder must be owned by the user. Secret-bearing files are 0600. Missing parents of these folders, such as `~/.local`, are created 0755, except `~/.config` (the XDG configuration folder), which is created 0700 as the XDG specification asks. Workbench runs with the user's umask plus 022, as sudo does, so nothing it or its tools create is group- or world-writable: its checks refuse such parents, tools and targets, and Ubuntu logins default to umask 002. An existing parent that others can write to stops Workbench with the folder and the `chmod go-w` that fixes it. WSL private state stays on the Linux filesystem; Windows target protection needs Windows ACL verification, not a claim that POSIX chmod suffices.

The hidden `--local-build` takes no value and selects the developer tree: the nearest ancestor of the current directory holding `.chezmoiroot` and `go.mod`, or exit 2 outside one. On `update` it installs only the tools that tree's `versions.toml` pins, so VERSION, `--bundle` and `--runtime-ready` are refused with exit 2. `--destination PATH` selects a configuration destination. Default destination is the actual current user's home. Full provisioning rejects an alternative destination because current scripts write `$HOME`, platform directories and external state independently of chezmoi's destination. Isolated full smoke tests therefore need a disposable OS user/VM. Reject relative runtime overrides, unsafe ownership, escaping symlink parents, source/destination aliases, targets overlapping source/runtime/state, unsupported state and non-regular input files before mutation. Runtime directories may live beneath the destination home but are never managed target paths. No recursive cleanup is authorized by an override.

Every chezmoi invocation supplies explicit `--source`, `--config`, `--destination`, `--persistent-state`, `--cache`, `--no-pager`, `--use-builtin-diff` and `--refresh-externals=never`. Source is the selected context root containing `.chezmoiroot`, not a guessed home source directory. Native config output contains `sourceDir = .../home`; retain answers as `[data]` only after validation, so Workbench's release/context selector remains authoritative. Existing configuration adoption copies validated data only, with explicit approval; never inherit arbitrary native hooks, external commands, source selection or Git auto-push configuration.

Previews, doctor and inspection do not create persistent state, native Git metadata, or missing answers. Any render scratch is ephemeral/private with copied native state; never invoke mutating native commands against live state to implement a preview. Audit template `output`, `lookPath`, modify executables and host probes separately from provisioning scripts. `--exclude scripts` still executes Python modify programs and evaluates templates. The WSL questionnaire makes host sizing probes conditional on missing values; only reviewed read-only probes are permitted. Do not open editors, remote sessions or repository code during discovery.

Release source render trust is the machine source digest `scripts/package-release.py` writes into `release.json` and stamps into that release's executable: the SHA-256 of one `<sha256>  <path>` line per `.chezmoiroot`/`home/` file, sorted by path. A release source (one with `release.json`) whose files, metadata or executable stamp differ is rejected, an unstamped build accepts no release source, and filename recognition alone cannot authorize executing a modify script during preview. A developer checkout selected with `--local-build` is the user's own tree: it is bound by its actual content digest, which enters the approved plan, so its templates render during preview like `chezmoi diff` would. A private verified source selection handles role-driven native removals without introducing another renderer. Runtime ancestors can be validated containers. Native may change only such a directory's mode, and only to one without group or other write; the plan lists it as a mode-only edit, and its checkpoint lets revert restore the mode. Nothing may remove or replace them. The checkpoint records such a folder with what macOS puts on `~/Library` and `~/Library/Application Support`: the default `group:everyone deny delete` ACL (any ACL entry that neither passes to new entries nor denies adding or removing them), and the hidden flag on a folder Workbench writes into. The configuration keeps both folders private (0700), as macOS creates them, and tightens a looser `Application Support`. It keeps `~/.config` private (0700) too and tightens a looser one, the same mode-only edit. When a checkpoint cannot record such a folder, as for any other flag, ACL or extended attribute on it, the plan stops with the `chmod` that matches the configuration; within the shared bin directory only the Workbench entry point is reserved.

The release channel is a build stamp, not a version order: the release workflow builds with `scripts/package-release.py --published`, which sets `internal/cli.buildPublished` in the executable, and `release.json` carries no channel field, so every release reads the bundle. `update` without VERSION reinstalls nothing when the installed release is already the latest and active. Otherwise, when the running program is the active release's own executable and is not stamped published, it installs the latest published release whatever the versions, naming the local build it replaces; any other program installs the latest only when it is newer than the active release. An explicit VERSION is installed as given. GitHub's latest release excludes pre-releases: a tag with a hyphen (`vX.Y.Z-rc.N`) is built `--published` and published with `gh release create --prerelease`, so `update` installs it only by name, keeps it while it is newer than the latest, and installs `vX.Y.Z` once published (semantic versioning orders the pre-release first). A pre-release gets no `CHANGELOG.md` section or commit; `cliff.toml` matches only full release tags (ADR 0011).

## Native initialization

[Native init](https://www.chezmoi.io/reference/commands/init/) always initializes a Git repository when `.git` is absent. In v2.70.3, [the implementation](https://github.com/twpayne/chezmoi/blob/v2.70.3/internal/cmd/initcmd.go) supports the built-in Git path. There is no `--no-git` flag. `execute-template --init` supplies simulated prompt functions; it is useful for fixtures but is not the interactive questionnaire.

Use this native sequence in the setup stage of `apply`. `update` installs the release and the pinned tools only and never runs it:

1. Verify the release archive; create a private application-context copy of its source, retaining the verified payload content hash. Staging and activation inside `update` do not perform this initialization.
2. Create a private native seed TOML containing validated existing `[data]` answers, or an empty seed for native terminal prompting. Do not put secret answers in command arguments or prompt-text flags. The canonical template owns conditional questions and derived role/WSL values.
3. Execute the following with absolute, prevalidated paths, no repository argument and no `--apply`:

   ```sh
   chezmoi --use-builtin-git=true --config "$seed" \
     --source "$context" --destination "$destination" \
     --persistent-state "$private_state" --cache "$private_cache" \
     init --config-path "$generated_config"
   ```

4. Validate the generated TOML/answers; atomically record private answers only. Recheck source payload identity and seal that context before target planning/application. Native `.git` metadata and host answers are excluded from payload identity and distributable assets. Do not exclude arbitrary source changes from identity merely because native metadata exists.

Probe evidence: on macOS 27.0 arm64, an extracted `git archive` of the source (no `.git`) plus complete private `[data]` inputs initialized without questions using `--no-tty`, generated a 0600 config, and applied files into a disposable destination with `--exclude scripts`, including the Python Codex modify program. A repeat init produced identical configuration. Native empty `.git` occupied 8 KiB in this probe, not a size guarantee. No remote or commits were created. A separate unrelated working-tree directory failed native containment validation. A `git.command=/usr/bin/true` experiment avoided metadata but is explicitly rejected as the product path; do not mask native operations with no-op executables.

Serialization contract: the canonical questionnaire uses structured native TOML serialization. Native `dict "name" .name | toToml` round-tripped quotes, backslash, comma, equals, newline and Unicode exactly. The implementation uses native `toToml` on structured data, preserving the canonical questions. Validate role/editor/mode rather than silently normalizing invalid persisted answers. Validate sizing strings, integer bounds and restart paths before downstream scripts. Machine identity fields reject control characters/newlines even though the serializer can represent them. Structured serialization is also required at each downstream TOML/JSON/Git/shell/PowerShell boundary: escaping the seed alone does not fix Python triple-quoted generated code, raw Git identities, shell substitutions or PowerShell quoting. Invalid Codex TOML fails without replacement. Do not reintroduce permissive fallback behavior.

## Consent and output

Select `--non-interactive`, `--approve-plan SHA256` and `--json` for automation. Without a terminal, mutation requires complete answers (saved with `init --answers-from FILE`) and the matching plan digest; `--yes` applies the saved selection for a person who trusts it and is not a substitute for reading the plan. A coding agent is refused `--yes` (exit 3). `--yes` with `--approve-plan`, `--choose` or `--reset` is an invalid invocation (exit 2), and so is `--choose` with `--approve-plan`; `migrate --apply` applies the same `--yes` and `--approve-plan` rules through the same check. Interactive `apply` approval follows the same displayed plan: a Bubble Tea list of the files and effects on the controlling terminal with the plan's checks as defaults, where `a` applies exactly that selection and q, esc and ctrl+c refuse. It is shown only when something is new to decide or a Workbench-owned file was edited outside it; otherwise the saved selection is applied after printing the plan, at a controlling terminal only (without one `apply` refuses unless `--approve-plan` or `--yes` is given, and a coding agent always needs `--approve-plan`; the refusal comes before any download or save), and `--choose` always asks. `revert` and `project` use that Yes/No prompt, where Enter alone, n, esc and ctrl+c all refuse. Recovery without `--checkpoint` offers the saved checkpoints in a huh picker at a terminal and otherwise lists them and blocks. `apply` asks for one approval, of the checked machine plan; `update` asks none, because it changes only Workbench's own files and keeps the replaced release, and `update --dry-run` still shows the install plan. Installing the release and setting up Workbench's pinned private tools need no separate approval, because running the command requests them. The native questionnaire asks only what the saved answers lack, or what `init --ask` names, and its answers never authorize configuration or provisioning. Cancelling it with esc or ctrl+c saves nothing and blocks, naming `workbench apply`. A signal (SIGINT, SIGTERM, SIGHUP) during any prompt ends it with the interruption code and writes nothing. If full preview needs missing prerequisites, return blocked and name `workbench update`, or `workbench apply` at a terminal, which sets them up (`workbench update --local-build` for a checkout, which installs the tools its `versions.toml` pins and which a coding agent may run); `apply` then produces the machine plan for approval. Missing unattended answers fail; never accept native prompt defaults silently. Prompt values stay off argv and out of logs.

The digest binds release/source content, dependency choices, which effects are checked (a changed saved selection returns conflict, exit 4), canonical destination/project scope, Workbench's runtime folders (config, data, state, cache and bin for `apply`; the config, data, state and cache folders the files move into for `migrate --apply`), so an approval given under other folders exits 4 before the plan is applied, native input/state hashes, current target images, file removals, external effects and selected privilege. Recompute it before writes; a changed input returns conflict. Do not persist low-entropy secret hashes in public output; expose only an opaque aggregate plan identity and redacted descriptions. Latest-mode provider changes that broaden the plan require renewed approval.

Ordinary apply includes selected configuration/provisioning only. Cleanup, tap removal, app updates, extension conflict removal, a system-wide package source (EPEL: the `epel` effect, on by default and listed only where the package manager is dnf), Windows registry/environment/default-distribution changes and system tuning must appear as individually named effects with recovery limitations. A plan lists a provisioning effect only when native chezmoi would run one of its scripts or change one of its files (`effectSources` in `internal/machine/effects.go`), so a once-only script that already ran is not presented as work; an effect without sources is always listed. Homebrew cleanup and tap removal (`brew-maintenance`) are a named effect of every full macOS plan; Windows host changes and system tuning stay disabled until explicitly selected; each listed app or formula Homebrew reports as outdated, from its index as it is (planning and the recheck set `HOMEBREW_NO_AUTO_UPDATE` and never refresh it; an apply not given `--approve-plan` runs `brew update` once on the real home, after tool setup and before it plans, so a person sees current updates, while `--dry-run` and `--approve-plan` never do and an approved digest still matches; `brew-maintenance` runs `brew update` at the end only for an apply that did not refresh at its start; a failed refresh only warns), is its own named update effect, except formulae providing the chezmoi or uv Workbench runs or whose upgrade would change them (a versioned Homebrew Python updates within its minor version, which Workbench still accepts), which the plan leaves out without a warning; a formula's effect names the other formulae Homebrew's dry run says its upgrade installs or updates, and the apply step sets `HOMEBREW_NO_ASK` so plan approval is the only prompt; apps installed outside Homebrew are left alone. On every platform, Codex and Claude Code each get an `update-codex` or `update-claude-code` effect when the copy the shell runs is older than its target (the `versions.toml` pin, or in latest mode the newest release on the channel the tool's own updater follows, for Claude Code the `autoUpdatesChannel` of its user settings (in `CLAUDE_CONFIG_DIR` when set) and managed settings files, both looked up side by side while planning, 3 seconds each; a failed lookup only warns): the plan reads how that copy was installed and its version from the installer's files without running it, never proposes a downgrade (a prerelease ranks below its release), names both versions, the installer and, in latest mode, the channel in the description the digest covers, and the apply ends at exactly that version (npm in the nvm Node it is in; Codex's standalone installer with `--release VERSION` in pinned mode, or `--release latest` in latest mode with the channel checked before, the selected release checked after in both; `claude install VERSION` run from VERSION's binary for the host platform once Anthropic's GPG-signed release manifest for VERSION is verified and that binary matches it, with the binary `claude install` downloads and installs itself checked against it after). A vendor installer's release reached through a launcher other than the one the installer makes (`~/.local/bin/claude`, `~/.local/bin/codex`) is named in a warning and left alone, and so is a native Claude Code update below the `minimumVersion` of its user or managed settings, which `claude install` would skip. An isolated `--destination` plans no agent or Homebrew updates. A Homebrew cask copy is one of the Homebrew updates on macOS, and a copy installed any other way is named in a warning and left alone (ADR 0009). Blanket unattended approval does not enable an omitted effect. No services/WSL restart, scheduled-task execution, credentials authentication or security-policy weakening is implied by setup. Existing AI trust/permission settings, the credential files the `env-files` effect creates and the Claude Code MCP servers the `claude-mcp` effect registers or removes are security-sensitive configuration effects and must be visible for controller/user policy ratification; this contract does not independently approve a new security policy.

Human output uses stdout for results and stderr for diagnostics/progress. At a terminal, planning, the recheck after approval, the Homebrew refresh and tool setup show one live status line (spinner, step, elapsed time) drawn by an inline Bubble Tea v2.0.10 program with a Bubbles v2.2.1 spinner and Lip Gloss v2.0.6 styles; it reads no input, so it sends no terminal queries and leaves the terminal mode and ctrl+c/ctrl+z alone, and it clears before any prompt or terminal handoff. Otherwise each step prints as a plain line. An interrupt during planning ends it with the interruption code, even inside probes whose failure only warns. A plan prints as a readable review of files, effects with their privilege and recovery, warnings and recovery limits, and `--json` carries the complete plan. At a terminal, component results carry a colored ✓, · or ✗, a successful run ends with a green ✓ summary (the result's `summary`), and a plan already shown at an approval prompt is not repeated; piped output and `NO_COLOR` get plain text. An interactive apply gives native chezmoi the controlling terminal as the foreground process group, so installers can prompt and their output appears live, then takes it back with SIGTTOU ignored so a job-control shell does not stop Workbench; before that, an apply at the terminal on macOS asks for the Mac password at most once. When a checked effect is marked `needs_admin` (Homebrew's installer while Homebrew is missing) it asks after the recheck and before any checkpoint, state write or script: `/usr/bin/sudo -n -v` first (a valid ticket asks nothing), else Workbench reads the password itself from the terminal without echo and checks it with `/usr/bin/sudo -k -S -v` (the password on standard input only, a minimal environment, no sudo ticket left behind), asking again after a wrong one; a wrong password three times, a non-administrator or a refusal ends the apply blocked (exit 3), ctrl+c interrupted (exit 130, the terminal's echo restored), with nothing changed. Otherwise it asks the first time a Homebrew command or the `touch-id-sudo` step's sudo needs it. Where sudo already asks for Touch ID (an active `auth` line naming `pam_tid.so` in `/etc/pam.d/sudo_local` or `/etc/pam.d/sudo`, both read by Workbench, a missing or unreadable file meaning off) Workbench reads no password and makes no helper or `WORKBENCH_SUDO_ASKPASS`: with a checked `needs_admin` effect and no valid ticket (`/usr/bin/sudo -n -v`) it runs `/usr/bin/sudo -v` on the terminal, in its own process group so ctrl+c reaches both, after one plain line saying why, and sudo asks by Touch ID or, where Touch ID cannot be used, with its own password prompt; a refusal, a non-administrator or three wrong passwords end the apply blocked (exit 3), ctrl+c interrupted (exit 130), with nothing changed, and an approval that `sudo -v` created is dropped with `sudo -k` when the apply ends. Homebrew's own sudo then asks for itself, by Touch ID or password, each time it needs it. The password stays in Workbench's memory for that apply and in its secret redaction set; it is never written to disk, the environment, arguments, logs, the plan or `--json`. For the whole native apply Workbench makes a private (0700) folder holding a `SUDO_ASKPASS` helper script and a Unix socket, and passes the script's path to the scripts as `WORKBENCH_SUDO_ASKPASS`; the darwin scripts give it to Homebrew's installer, to `brew` and to the one sudo command of the `touch-id-sudo` step as `SUDO_ASKPASS`, and to nothing else, and it is never in planning or probe environments. The helper holds no password: it asks Workbench on the socket, which answers only while the apply runs and only processes the apply started (the connecting process's id from `LOCAL_PEERPID`, its parent ids followed to Workbench's own; Workbench itself and unrelated processes get nothing). When Workbench holds none yet, the helper, which runs in the terminal's foreground process group, asks on `/dev/tty`, checks the answer with `sudo -k -S -v` and gives only a correct one to Workbench to remember; three wrong answers fail that one sudo. The folder is removed when the apply ends, however it ends, and when a helper got the password, the sudo approval sudo then kept for the terminal is dropped with `sudo -k`. The terminal is handed back to Workbench with the settings it was lent with, so a ctrl+c at the helper's prompt cannot leave echo off. Homebrew drops sudo approval (`sudo --reset-timestamp`) each time brew runs, on purpose, so Workbench keeps the password rather than a ticket, and the approved plan stands in for Homebrew's per-command approval while the apply runs. `needs_admin` is a finding of the plan like a probe's delta, set from Homebrew's absence, and is not in the digest. Without a terminal nobody is asked and no helper is made: a valid ticket is used, and without one only a plan that must install Homebrew is refused (exit 3, before any change); unattended runs stream redacted output lines on stderr. Neither has a deadline: provisioning runs until done or interrupted, and the caller's supervisor owns any time limit. Native apply runs with `--keep-going`, so a script that exits nonzero never stops the scripts after it, and chezmoi does not record a failed `run_once_`/`run_onchange_` script as run. A script names each part it could not do in the file named by `WORKBENCH_EFFECT_REPORT` (one `effect`, tab, `reason` line each; an effect with several lines shows every reason), including a part skipped because an earlier step did not install what it needs, goes on with the parts that do not need it and ends nonzero (a script that runs on every apply may end 0). chezmoi runs every `.sh` script through a step runner Workbench writes in its private scratch folder (the private config's `interpreters.sh`), which runs it with `bash` and, when it ends nonzero below 128 without having named any of its effects, names each checked effect it owns with the exit status; a script ended by a signal is not named. When every failed script named itself and every target matches its approved image, the apply finishes like a successful one, shows each named effect `blocked` with its reasons and ends 3 (`A step could not be done (marked blocked above); everything else was applied, and the next apply tries it again`). Otherwise apply exits 5 with `Setup did not finish (CAUSE); the other steps ran and what they did is kept. The output above says why; fix that, then run COMMAND apply again.` (COMMAND from `WorkbenchCommand`), the files stay recorded as written and the unfinished apply stays recorded until a rerun settles it; an interruption keeps its own message and code. Captured probes stay bounded and report a failed tool's redacted stderr tail. ## Checkpoints and current state

Use random operation/checkpoint UUIDs, recording scope (`machine` or canonical project root), creation time, before/applied release identity (for project checkpoints, the policy ID such as `python-v1`), pre-images, post-images and effect results. `revert` and `project revert [PATH]` see only that scope's checkpoints. `revert --checkpoint ID` and `project revert [PATH] --checkpoint ID` restore that operation's pre-images after full preflight. With no selector, a terminal picks one from the list, otherwise the list is shown and an explicit selection is required. An unknown ID fails with the IDs to choose from. A target whose outcome the journal could not record, because Workbench was stopped or crashed while a writer ran, is decided by recovery preflight from what it holds now, never by inferred success or blind restore: exactly its post-image counts as written and exactly its pre-image as untouched. For a forward native run, a post-image apart from the group native creation gave it also counts as written, and recovery gives it the approved group under the revert's consent before restoring anything. Any other content blocks like a later edit, naming the file; an unknown outcome never blocks later applies.

Preflight every target before restoring any, record type/mode/group/link target as well as bytes, and stop on later edits or unsupported filesystem metadata. A folder a restore would remove that now holds an entry the restore does not remove (a file Workbench did not write, or a folder kept for that reason) stays: revert leaves it, and every folder holding it, with its recorded outcome unchanged, restores the other targets and lists each kept folder as a plan warning and in the result. A forward apply that would remove such a folder is refused before any write. Hard links, special files, escaping symlinks, unverified ACL semantics and broad directory replacement are blocked until preservation is supported. Native machine planning rejects output modes granting group permissions beyond other permissions, such as 0640/0750: native temporary-file ownership cannot yet preserve those atomically. Workbench runs native and its scripts with `TMPDIR` set to the run's private scratch folder (mode 0700, made in Workbench's own temporary folder and removed after the run). Native stages each file it writes there whenever that folder is on the target's file system, so the file arrives with the scratch folder's group and Workbench then gives it the approved group; planning refuses, before any write, a file whose folder gives new files a group the user is not a member of when the scratch folder gives a different one, because that correction would fail. For supported modes, descriptor-bound exact-image checks precede any post-native group correction. After a native run that failed or was interrupted (the process runner kills native's process group and waits for it first), the same check and correction apply one target at a time: a target whose content, type and mode already match its approved image gets the approved group, so the checkpoint records it as written, and any other target is left as it is. The shared project/recovery writer sets group before chmod and atomic replacement. Revert creates its own recoverable operation. It does not run the old release, native provisioning scripts or project dependency hooks. Packages, extensions, user environment/registry, loaded fonts, kernel values and external services are outside file recovery even if nearby configuration files are restored.

Retention: each scope keeps the 20 most recent **forward-operation** checkpoints. Before each forward mutation, reserve its paired recovery record and bounded journal capacity as well as its image storage. At 20, the plan lists removal of the oldest settled (complete or failed) checkpoint and its pair as a named `checkpoint-retention` effect that is fixed (always checked, with no box to untick), so consent covers it; the removal happens under the held locks just before the new checkpoint is reserved. When none is settled, the effect names the oldest running, partial or unknown checkpoint that a newer checkpoint supersedes (its description says "superseded incomplete"); the checkpoint named by the recorded partial operation is never removed, and recovery of retained checkpoints stays available. An incomplete checkpoint does not block later applies: each apply still requires every target to equal its previewed image, and the incomplete checkpoint keeps its images and stays revertable until it is superseded and pruned. The recorded partial operation stays until a later approved apply to the same destination finishes or recovery restores its checkpoint; an apply with no target changes settles it because its plan found every target already matching, while an apply to another destination (whether or not it changes files), or a revert of a machine checkpoint other than the one the record names, is blocked while it stays. No age-based deletion. An apply with no target changes allocates no checkpoint; one whose files all match, with no effect checked, no changed selection to save and no recorded partial operation to settle, writes nothing, so it asks for no approval and says `Nothing to apply; this machine already matches`. Users never need to delete checkpoint files to recover.

Recovery uses the reserved pair, not another forward slot: retain the original checkpoint and one separately selectable recovery checkpoint with reversed pre/post-image references. Each scope therefore has at most 20 forward and 20 paired recovery checkpoints. Restore, undo-of-restore and retries reuse that pair's bounded resumable journal; they do not recursively allocate checkpoints. A new recovery attempt has its own operation identity and current progress, and may replace a completed attempt's journal only after both image sets and the selectable recovery checkpoint remain durable. An interrupted attempt must resume or reconcile before reusing its journal. Preserve known per-target images after partial application; an unknown outcome is decided by the preflight rule above. This bounds recovery storage without deleting either checkpoint or sacrificing the ability to undo a completed restore.

Conservative implemented caps: 256 targets, 8 MiB per image, 32 MiB aggregate raw pre/post images per forward operation, 50 MiB serialized per pair and 1 GiB per scope. Reserve two 64 KiB journal slots before target writes. Refuse forward mutation if images and protected recovery capacity cannot fit; a recovery on a full disk can still stop after restoring files with exit 5 and the checkpoint retained. A journal slot torn by an interrupted save is tolerated: the other slot, the last durably recorded state, is used, and only when both are invalid does the scope report "Invalid recovery journal". A stray Finder `.DS_Store` in the checkpoint scope is ignored. The measured source corpus was about 156 KiB with a 24,417-byte largest file; a representative native uv lockfile was 9,988 bytes. This supports headroom for those fixtures, not a universal capacity/performance claim. Native release qualification remains open. There is no separate cleanup command; plan-approved retention is the only removal of a published checkpoint, and a failed reservation (a `.prepare-*` directory, which holds no recovery data) is discarded automatically.

Persist `schema_version: 1` in current state/journals and validate all required fields, identities, scopes and image references before use. Unknown versions or malformed state stop without conversion/deletion. A single private active-release record selects a matched executable/source release. Each record replacement is atomic, but activation also changes the entry-point symlink: a private journal detects interrupted mismatches and requires explicit install resumption. Preserve the prior verified runtime; never claim whole-filesystem atomicity. After a successful activation, delete only the plan-listed older releases (keeping the new and replaced releases), and the setup contexts and private tool versions that no kept release or recorded dependency uses. A partial apply retains the prior successful configuration identity plus a partial-operation record. Hold shared release/state and selected scope locks in consistent order and recheck filesystem inputs; external package managers are not transactional. No compatibility matrix or migration layer.

## Release gates and short validation checklist

Release integrity requires target/version/content manifest validation, SHA-256 verification of every payload member against the in-bundle manifest before staging (the installer runs the bundle's own executable to do this; there is no external checksum), file-count/size limits, regular-file/directory-only payloads initially, and rejection of traversal, links, devices, duplicate members and mismatched expected layout. The in-bundle SHA-256 manifest only detects corruption; it does not establish publisher trust. By the owner's decision, releases publish on `v*` tags to a public repository, unsigned and with no redistribution license; native capacity qualification remains open. Implemented bundle limits are 128 MiB compressed/download, 256 MiB expanded, 4,096 archive members and 1 MiB metadata. Payloads include the matched executable/source, four portable Python policy files and linked dependency/runtime license notices. The bundle NOTICE grants no Workbench redistribution license, and no signing identity is used.

Use the existing `scripts/render-check.sh` and CI job. The helper owns isolated source/config/destination/cache/persistent-state paths; a temporary destination alone is not enough. Reuse role/mode rendering and simulated WSL syntax checks. Simulation on macOS does not prove native Linux provisioning or Windows execution; current results belong in the acceptance record.

For each qualified native target, record OS/CPU/tool versions and a short disposable-user smoke: initialization without external Git; all role/mode config renders; repeated approved apply convergence; denied/absent privilege; actual shell/Git/editor/theme/tmux/runtime/global-tool effects; explicit optional-effect denial; unchanged recovery and later-edit conflict. WSL additionally needs Windows home paths with spaces/non-C-drive layouts, Terminal/PowerShell preservation, private ACL checks and individually reported registry/PATH/default-distribution/sysctl effects. Never restart WSL merely to test a `.wslconfig` change. Existing files/credentials must be synthetic. Short checks of missing prerequisites, incomplete inputs, malformed config, source/destination overlap and edited checkpoint targets establish safety boundaries; no new testing framework or broad lifecycle matrix.

Routine verification remains formatting/lint/build and brief manual probes. Introduce automated checks only where the implementation could cause catastrophic data loss, credential exposure or unauthorized execution. No performance superiority or resource budget is established by these probes. Additional managers/languages, native Windows, automatic maintenance, production capacity qualification and publication trust remain explicit later decisions; the affected operation stays blocked until its gate is met.
